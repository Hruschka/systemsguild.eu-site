Status: **approved 2026-09-09.** Decisions: Jekyll on GitHub Pages, public repository, **no content is dropped** (every page, post, event and media file is migrated), editors maintain Markdown files directly.

## 2. Target: what "simplest possible" looks like

**Goal:** Markdown files in a Git repository, built and hosted for free on GitHub Pages, custom domain systemsguild.eu, HTTPS, no PHP, no database, no plugins to update, no license fees.

### Options considered

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| **A. Jekyll on GitHub Pages** | Markdown + Liquid, posts/tags/feed/SEO built in, same stack as arc42.org | Ruby needed for local preview | **Recommended** |
| B. Hugo + GitHub Actions | Very fast, single binary | Go templating is less familiar, needs a workflow file, more ceremony for a 45-page site | Good alternative |
| C. Eleventy (11ty) + GitHub Actions | Flexible, JS ecosystem | Needs Node toolchain and workflow, more decisions to make | Not needed here |
| D. "Freeze" WordPress with a static-export plugin | Fastest to get static | Keeps the paid Impreza CSS/JS (license-unclear), not Markdown, not editable | Rejected |

Recommendation: **Option A, Jekyll.** The site is small, has no interactive features worth keeping, and the arc42.org site already uses the same setup, so the toolchain is familiar.

**Build variant (decided 2026-09-09 after testing):** GitHub Pages' native build uses Jekyll 3.9, which no longer runs on current Ruby (4.0 on the development machine: `undefined method 'tainted?'`). Jekyll 4.4 with jekyll-feed, jekyll-seo-tag, jekyll-sitemap and jekyll-redirect-from was verified to build locally. The site therefore uses **Jekyll 4.4 built by the official GitHub Actions Pages workflow** (`ruby/setup-ruby` + `jekyll build` + `actions/deploy-pages`). This is GitHub's documented path for Jekyll 4, costs nothing, and gives identical editing (Markdown + YAML in Git) with a current toolchain.

## 3. Migration steps

### Phase 0: Repository skeleton (½ day)
1. `git init`, create GitHub repository (public, or private with a paid GitHub plan for Pages).
2. Jekyll skeleton: `_config.yml`, `Gemfile` with `jekyll ~> 4.4` and plugins, `_layouts/`, `_includes/`, `assets/css/main.css`, `.github/workflows/pages.yml`.
3. Rebuild the layout from the screenshots in `reference/original-site/screenshots/`: header, footer, content column, colors above.
4. Enable GitHub Pages (source: GitHub Actions), verify the empty site deploys.

### Phase 1: Export content (½ day, scripted)
The WordPress REST API is open and returns clean data, so no admin access or database dump is needed:
- `GET /wp-json/wp/v2/posts?per_page=100` → 28 posts with rendered HTML, date, slug, tags
- `GET /wp-json/wp/v2/pages?per_page=100` → 15 pages with rendered HTML
- `GET /wp-json/wp/v2/media?per_page=100` → 98 download URLs
- `GET /wp-json/wp/v2/tags`, `/categories` → tag and category names

A Python script (`tools/export_wp.py`) downloads all of this to `reference/export/` and `assets/images/`, and rewrites image URLs to local paths.

### Phase 2: Convert posts automatically (½ day)
- Post HTML is Gutenberg output (paragraphs, `media-text` blocks with the skull image). Convert with `pandoc -f html -t gfm` or `markdownify`, then post-process the skull blocks into a small include, e.g. `{% include rule.html text="Teamwork means doing what you're told." %}`.
- Front matter: `title`, `date`, `tags`, `author`, `permalink: /<slug>`.
- Spot-check 3 posts, then run for all 28.

### Phase 3: Convert pages (1 to 1½ days, mostly manual)
WPBakery wraps content in nested `vc_row`/`vc_column` divs, so automatic conversion gives poor results. With 12 real pages, manual conversion is faster and cleaner:
- Text pages (about, culture, culture-at-work, riskology, contact, 6 person pages): strip to text, write Markdown, place images with a small `figure` include for left/right floats.
- Guild Books: transcribe into `_data/books.yml` (title, authors, blurb, cover, links). Rendered by `guild-books.md` via a loop.
- Home page: `index.html` layout with hero, latest post, NEWS include; NEWS items go into `_data/news.yml`.
- Fix the footer text (currently a placeholder).

### Phase 4: URLs, redirects, quality (½ day)
- Keep every existing URL: posts and pages via `permalink`, `/category/culture-killers`, `/tag/<tag>` via generated pages, `/feed` via jekyll-feed.
- `jekyll-redirect-from` for `/author/*` → person pages, `/event/killer` → `/events/`.
- Run a link checker (`htmlproofer` or `lychee`) against the local build.
- Compare each page side by side with the screenshots; check mobile width (414px screenshot is in the reference folder).

### Phase 5: Cutover (½ day plus DNS propagation)
1. Add `CNAME` file with `systemsguild.eu`, configure the custom domain in GitHub Pages, enforce HTTPS.
2. At the registrar: `A`/`AAAA` records for the apex to GitHub Pages IPs, `www` CNAME to `<org>.github.io`.
3. Keep the WordPress installation running read-only for 2 to 4 weeks as a fallback (reachable via a temporary subdomain if needed), then cancel the WordPress hosting.

**Total estimate: about 4 working days of effort, spread over the DNS waiting time.**

## 4. Editorial workflow after migration
- A new weekly Culture Killer post = one Markdown file in `_posts/` (GitHub web editor is sufficient, no local tooling required). The home page updates automatically because it shows the newest post.
- A news item = one entry in `_data/news.yml`.
- A new book = one entry in `_data/books.yml` plus a cover image.
- Every change is a Git commit; GitHub Pages rebuilds in about a minute.

## 5. Decisions taken (2026-09-09)
1. **Generator:** Jekyll, built natively by GitHub Pages.
2. **Repository:** public GitHub repository.
3. **Content:** nothing is dropped. All 15 pages (including WordPress leftovers, unlinked), all 28 posts, the event, all 98 media files and the contact details are migrated. Only non-content plumbing is left behind: comment forms (no comments exist), the dead analytics tag, the theme search widget.
4. **Editors** edit Markdown and YAML data files directly in Git. No CMS layer.

## 6. Remaining risks
- Some lazy-loaded images (portraits, book covers) did not render in the headless reference screenshots. Use the live site as visual reference until it is switched off.
- The contact form plugin is loaded on the contact page, but the page content is a list of addresses. Addresses become `mailto:` links; if a form is ever wanted, a free form service can be added.
